\section{Purpose and Scope}
This document states what the System's software must do. Each requirement is
one sentence with ``shall'', traced to where it comes from, and given a
verification method [2,~Sec.~1]. Together, the requirements cover everything
the earlier documents ask of the software: every control and every must-work
and must-not-work function of the hazard analysis, every scenario, capability
and objective of the ConOps, and NASA's rules for safety-critical software.

It covers the three software items of the Software Classification: the
controller firmware, the onboard computer software and the ground software,
all Class~B and safety-critical [4,~Secs.~3.0 and 4.0]. Bench test tools and
firmware build tools follow the rules of their own class and are not covered.

\noindent\textbf{How to read it.} Section~3.0 introduces the software items
and the table columns. Sections~4.0 to 6.0 give the requirements of each item,
and Section~7.0 those that apply to all three. Appendix~A shows, item by item,
that nothing the earlier documents ask for is left out.

\section{Overview}

\subsection{Software Items}
A software item is one program that is built, tested and released as a unit
[2,~Sec.~3.2]. Requirements are organised by software item; the System has
three:
\begin{description}[leftmargin=4.8cm]
\item[Controller firmware] Runs on the controller: acts on commands, reports
  its state, and returns to working firmware on its own.
\item[Onboard computer software] Runs on the onboard computer: checks commands
  and firmware, stores reports, watches the controller, and restores it.
\item[Ground software] Runs in the mission operations center: prepares and
  checks commands and firmware, and keeps every report.
\end{description}
They meet over the radio link, the two data-link connections, the
reprogramming link and the operator interface [3,~Sec.~3.3].

The ConOps says which item does most functions. For the few it leaves open,
this document assigns one:
\begin{itemize}
\item the onboard computer and the controller both check the arming command
  before a dangerous command, so that one fault cannot let it through;
\item the controller answers every command and tests itself;
\item the onboard computer holds scheduled commands until they run, refuses
  new firmware during a trial, numbers reports, compares the onboard clock with
  ground time, and clears the controller's kept data when it restores it.
\end{itemize}

\subsection{Table Columns}
\begin{itemize}
\item \textbf{ID:} REQ-001 onward, in one sequence. An ID is never reused.
\item \textbf{Requirement:} one claim, in one sentence.
\item \textbf{Source:} where the requirement comes from. ``H-1 control 3'' is
  control 3 of hazard report H-1, and ``H-4 cause e'' a cause of that report
  [5,~Sec.~6.0]. A hazard named alone, such as ``H-14'', is a moderate or
  negligible hazard, which has no report [5,~Sec.~4.0]. Scenarios, capabilities and
  objectives (O) are those of the ConOps [3,~Secs.~3.1, 3.5 and 6.0]. SWE-$n$ is
  rule $n$ of NPR 7150.2D [1,~App.~C, pp.~56--78]. A shared cause is a finding
  of the hazard analysis [5,~Sec.~5.2].
\item \textbf{Verified by} [6,~Sec.~5.3.1.2.1, p.~92]: TEST, using the product
  to obtain detailed data; DEMONSTRATION, using it to show the requirement is
  met, without detailed data; INSPECTION, examining the product or its
  records; ANALYSIS, modelling or calculation.
\end{itemize}
