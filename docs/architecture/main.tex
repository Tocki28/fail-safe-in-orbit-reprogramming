\section{Purpose and Scope}
This document records the software architecture of the System: its
components, what each does, how they connect, and the design decisions behind
them [1,~Sec.~4.2.3, p.~33]. It covers the three software items of the
requirements [6,~Sec.~3.1].

The architecture concentrates on ``the most pressing risks'' [3,~Sec.~4]: the
eight catastrophic and critical hazards that do not yet meet the fault
tolerance rule [5,~Sec.~5.0]. The software qualities it is built for are the
two a high-risk project emphasises, fault tolerance and security
[3,~Sec.~4], and the testability the requirements demand.

The architecture remains strictly hardware-agnostic, defining functional
component behavior rather than the hardware that executes it, and concludes
with the capabilities the hardware must provide. Detailed component designs,
including specific algorithms and data structures, are documented before each
component is implemented [1,~Sec.~4.3.2, p.~34].

\noindent\textbf{How to read it.} Section~\ref{sec:overview} shows every
component and one update on two figures. Section~\ref{sec:decisions} holds the design
decisions, each with the options weighed and the hazards it targets.
Section~\ref{sec:components} gives each component's role and the requirements
it meets. Section~\ref{sec:hardware} lists what the hardware must provide.

\section{System Overview}
\label{sec:overview}
The System has three software items [6,~Sec.~3.1], each made of components
(Figure~\ref{fig:overview}). The ground software builds and checks
the operator's commands, singly or as a planned sequence. It checks each
firmware release the operator approves, signs it, checks the signed result,
and encrypts everything as it is sent. It keeps every report that comes back. The onboard computer software checks everything that arrives and passes
it on; between contacts it stores the controller's reports, watches the
controller, and restores it when no firmware can run. The controller firmware
acts on commands, reports its state and handles its own faults. It tries new
firmware before keeping it and returns to working firmware on its own when the
new firmware fails: a bootloader chooses which copy runs, and the
last-resort firmware takes over when the main firmware cannot.
Figure~\ref{fig:update} follows one update from release to confirmed firmware.

\section{Constraints}
Three constraints of the ConOps change the design [4,~Secs.~1.1.2 and 8.0].
\begin{description}
\item[C-3] System development is conducted by a single engineer. Component
  independence is achieved through isolated software codebases rather than
  organizational team separation; one engineer writing every codebase limits
  their diversity.
\item[R-4] The space segment relies on a single onboard computer. A spacecraft
  can carry a second, redundant one, as the Mars Reconnaissance Orbiter does
  [12,~App.~F.2.15, Lesson 2041, p.~197]; how many is a spacecraft decision,
  outside this project. Its permanent failure halts command handling,
  telemetry reporting and firmware restoration. This single-point failure risk
  is formally accepted, so H-4 does not meet the fault tolerance rule
  [5,~Sec.~5.2].
\item[C-4] The onboard computer software and the controller firmware execute on
  two given development boards. The architectural design remains
  hardware-agnostic: it names no board, only what a board must have.
\end{description}

\section{Design Decisions}
\label{sec:decisions}
Each decision targets hazards that do not yet meet the fault tolerance rule
[5,~Sec.~5.2]. It states the problem, weighs the options, and lists the
requirements the choice added to the requirements [6,~App.~A.9]. Where a proven design exists, it is one of the options
[3,~Sec.~4].

Options are compared by the smallest number of failures that, together, cause
the hazard with that option in place. A catastrophic hazard needs at least three, a
critical one two [5,~Sec.~3.3]. The counts leave out the permanent loss
of the onboard computer, an accepted risk (R-4). They are design targets, which
the hazard analysis confirms in its design phase [5,~Sec.~1.0]. In each
options table, the last column marks the option the decision picks (YES) and
the options it rejects (NO).

\subsection{Start-Up and Fall-Back}
\label{sec:startup}
\field{Problem} Every firmware copy is started by the same bootloader and
depends on the data it keeps over restarts. A defect in the bootloader, or kept
data it cannot handle, stops every copy, and today's restore writes back the
same bootloader, so the defect returns [5,~Sec.~5.2]. One failure is then
enough for H-8, the controller stopping between contacts with nothing on board
to bring it back, and for H-1, the controller left with no firmware it can run
and no way to restore it.

\smallskip
{\small\noindent\begin{tabularx}{\textwidth}{@{}l>{\raggedright\arraybackslash}Xcc@{}}
\toprule
 & Option & \sev{H-8}{CRITICAL} & Chosen \\
\midrule
a & No bootloader: the last-resort firmware is the first code to run and decides which copy runs. A defect in it stops every start, and the restore puts the same firmware back, so the controller stays down until the ground loads a correction at the next contact. & 1 & NO \\
b & MCUboot's design [9,~Sec.~Boot Swap Types]: a small bootloader runs first, runs a new copy as a test and returns to the old copy unless the new one confirms itself. It survives a defect in any copy, but not one in the bootloader itself: that stops every start, and the restore writes the same bootloader back. & 1 & NO \\
c & Option b, plus a last-resort firmware sharing no code with the bootloader or the copies. When the bootloader fails, the controller goes silent and the onboard computer restores it, putting the last-resort firmware where the bootloader was, so it runs first (Figure~\ref{fig:memory}). The controller stays down only if a second failure follows: a defect in the last-resort firmware, or a failed restore. & 2 & YES \\
\bottomrule
\end{tabularx}}


\field{Choice} Option c, shown in Figures~\ref{fig:startup} and
\ref{fig:memory}. It keeps MCUboot's test and revert, which exists to keep bad
firmware from leaving a device unusable [9,~Sec.~Boot Swap Types], and adds a
last-resort firmware sharing no code with the rest [6,~REQ-009]. The
last-resort firmware is the controller's safe mode: it still accepts commands
from the ground [12,~Sec.~6.4.3.2.4, p.~85]. H-1, which also needs the
ground's way in, is decided in Section~\ref{sec:wayback}.

\subsection{The Way Back In}
\label{sec:wayback}
\field{Problem} When the bootloader is broken (Section~\ref{sec:startup}),
the controller runs nothing, and only a restore can bring it back. A restore
that needed any software on the controller to receive it would fail at exactly
that moment, which the requirements forbid [6,~REQ-056]. The restore therefore
needs a way into the controller's memory that works with nothing running on
it, and the ground needs the same way in to load corrected firmware
[6,~REQ-058]. Targets H-1, the controller left with no firmware it can run and
no way to restore it. The same way in also serves H-3 and H-4.

\smallskip
{\small\noindent\begin{tabularx}{\textwidth}{@{}l>{\raggedright\arraybackslash}Xcc@{}}
\toprule
 & Option & \sev{H-1}{CATASTROPHIC} & Chosen \\
\midrule
a & The controller is asked to restore itself, as in MCUboot's serial recovery, which runs inside the bootloader [13,~Sec.~Entering Serial Recovery Mode]. A broken bootloader means nothing receives the order and nothing can load a correction. & 1 & NO \\
b & One separate way in that needs nothing running on the controller; the onboard computer drives it and can restart the controller. A broken bootloader is bypassed, but if this way in also breaks, nothing reaches the controller. & 2 & NO \\
c & Two separate ways in that share nothing: the controller's debug port, which writes memory directly with the processor stopped, and its factory loader, which a boot pin starts instead of our bootloader. A broken bootloader and one broken way in still leave the other. Each way in has its own driver on the onboard computer; a defect in the restore program that uses both is corrected by the system outside this project (A-6), as for H-3. & 3 & YES \\
\bottomrule
\end{tabularx}}


\field{Choice} Option c. It follows the principle of hardware
commands, which a spacecraft executes on receipt without any flight software
[11,~Sec.~3.2, p.~9]. Such a command let the Spirit rover's team regain control
while its flight software kept resetting: it made the software start without
its flash memory [10,~pp.~4 and 9]. Two ways in are the fewest that meet the
rule. They still share the controller's memory and its reset wire; the hazard
analysis counts these shared causes when it is re-run on this design.

The debug port stays open in flight. After launch nobody can reach the hardware
(A-1), and locking the port would remove a way in. Because the port writes
memory around the controller's own checks, the restore writes only images that
have passed the same checks as an update, the bootloader included
[6,~REQ-118]; the port gives an attacker nothing the onboard computer has not
already checked. Before launch the hardware can be reached during integration
and testing; protecting it then is a ground procedure outside this System.

\field{Adds}
\begin{itemize}
\item REQ-122: The reprogramming link shall have two connections, independent of each other: the controller's debug port and its factory loader, each able to load the controller's memory whatever that memory holds.
\item REQ-123: The onboard computer software shall drive the debug port and the factory loader with separate drivers that share no code.
\item REQ-124: The onboard computer software shall be able to restart the controller.
\item REQ-125: No controller firmware shall be able to disable the debug port or the factory loader.
\end{itemize}

% ---------------------------------------------------------------- 5.3
\needspace{9\baselineskip}
\subsection{Restore Apart From Update}
\label{sec:apart}
\field{Problem} New firmware can reach the controller in two ways. In the
normal update, the onboard computer sends it over the data link to the
controller's running firmware, which writes it into memory. In the restore,
the onboard computer writes it into the controller's memory itself, through the
reprogramming link [6,~REQ-058]. Both start on the onboard computer, from a
copy of the firmware stored there. If one program did both jobs from one stored
copy, a single defect in that program, or a single damaged copy, would block
both ways at once. New firmware could then reach the controller only after the
system outside this project corrects the onboard computer's software (A-6)
[5,~Sec.~5.2]. Targets H-3, new firmware no longer able to reach the
controller.

\smallskip
{\small\noindent\begin{tabularx}{\textwidth}{@{}l>{\raggedright\arraybackslash}Xcc@{}}
\toprule
 & Option & \sev{H-3}{CATASTROPHIC} & Chosen \\
\midrule
a & One program does both the update and the restore, and both read the same stored copy of the firmware. One defect in that program, or damage to that copy, blocks both ways; the only barrier left is the outside system correcting the onboard computer (A-6). & 2 & NO \\
b & Two separate programs, the update manager and the restore program, each with its own code and its own stored copy of the firmware. Blocking both ways takes a defect in each program, and the outside correction failing as well. Both still rely on the same onboard computer software for the checks on every image [6,~REQ-118]: a defect there that refuses every image blocks both ways, with the outside correction failing. & 2 & YES \\
\bottomrule
\end{tabularx}}


\field{Choice} Option b. Apart from the checks, the two programs share nothing
that one defect could reach: when the update fails, the restore still works,
and the other way round. Every cause then takes three failures except a defect
in the checks both programs rely on, which takes two. Both programs use the
same checks so that the debug port gives an attacker nothing the onboard
computer has not checked (Section~\ref{sec:wayback}); that remaining cause is
an accepted risk.

\field{Adds}
\begin{itemize}
\item REQ-126: The restore program shall share no code or stored data with the update manager.
\end{itemize}

\needspace{9\baselineskip}
\subsection{Proof of Origin}
\label{sec:origin}
\field{Problem} The spacecraft must act only on commands and firmware that
really come from the operator. Today a single key proves this for both
[5,~Sec.~5.2]. Whoever steals that key can send commands and upload firmware
that pass every check on board, as if they were the operator. Targets H-2,
firmware from someone else running on the controller, and H-5, someone else
commanding the System.

\smallskip
{\small\noindent\begin{tabularx}{\textwidth}{@{}l>{\raggedright\arraybackslash}Xccc@{}}
\toprule
 & Option & \sev{H-2}{CATASTROPHIC} & \sev{H-5}{CATASTROPHIC} & Chosen \\
\midrule
a & One shared secret: the same secret is stored on the ground and on the spacecraft, and every command and image carries a code computed from it. Whoever learns the secret, from the ground or by reading the spacecraft's memory, can make commands and images that pass every check. & 1 & 1 & NO \\
b & One digital signature: the ground signs every command and image with a signing key that never leaves the ground. The spacecraft holds only a checking key, which can check a signature but cannot make one, as in MCUboot [9,~Sec.~Security]. Reading the spacecraft's memory gives nothing away, but whoever steals the one signing key from the ground can sign anything. & 1 & 1 & NO \\
c & Encryption and one signature: every command and image is also encrypted, so the spacecraft accepts only what was encrypted with the right key [11,~Sec.~4.1.1, p.~9]. The encryption key and the signing key are kept in two separate places on the ground: the encryption key only at the link encryptor, where transmissions are made, and the signing key in the ground software's key store. A false command or image takes stealing both keys. & 2 & 2 & NO \\
d & As c, plus a second signature made with a third key held on a hardware security key the operator carries, which signs inside itself and never lets the key out. A false command or image takes stealing all three keys, from three places. & 3 & 3 & YES \\
\bottomrule
\end{tabularx}}


\field{Choice} Option d, shown in Figure~\ref{fig:origin}.
Encryption is required along the whole command chain, from the operations
center to execution on board [11,~Secs.~3.2 and 4.1.1, pp.~8--9], and
encryption together with signatures is the recommended defence in depth
[11,~Sec.~4.1.1.c, p.~10]. The controller checks firmware signatures again
before running it [6,~REQ-006], with different checking code from the onboard
computer's, so that one defect in that code cannot let forged firmware through
both checks [8,~Sec.~7.4.2, p.~141]. The encryption key also sits on the
onboard computer, which must decrypt; taking it from there means taking over
the onboard computer, which would already give control of the whole System.
The hazard analysis, re-run on this design, finds two failures for H-2 and H-5
rather than three: one code checks both signatures, and the restore writes
past the controller's check. The author accepted that risk [5,~Sec.~8.3].

\item REQ-130: The controller firmware shall check firmware signatures with code different from the onboard computer software's.
\end{itemize}

\subsection{Two Clocks}
\label{sec:clocks}
\field{Problem} The onboard computer's clock decides when a command expires,
when an arming command times out, when a scheduled command runs, which time
each report is stamped with, and when a trial ends. Between contacts nothing
checks that clock. If it jumps or drifts, a scheduled command runs at the
wrong time and every report shows a wrong time, and nobody notices before the
next contact [5,~Sec.~5.2]. Targets H-6, here a scheduled command run at the
wrong time, and H-9, here reports shown with wrong times.

\smallskip
{\small\noindent\begin{tabularx}{\textwidth}{@{}l>{\raggedright\arraybackslash}Xccc@{}}
\toprule
 & Option & \sev{H-6}{CRITICAL} & \sev{H-9}{CRITICAL} & Chosen \\
\midrule
a & One clock, the onboard computer's, compared with the time sent from the ground only during contacts [6,~REQ-072]. Between contacts, a wrong clock runs scheduled commands at the wrong time and stamps wrong times on reports, and nothing notices. & 1 & 1 & NO \\
b & Counters instead of times where possible: every report and command is numbered in order. The order survives a wrong clock, but a scheduled command still needs to know when to run, and a report still needs a time. & 1 & 1 & NO \\
c & A second clock in the controller, running from its own time source and set only by time values sent from the ground, never from the onboard computer's clock. A scheduled command runs only when both clocks agree on the time, and every report carries both times, so a wrong clock on one side shows up against the other. A wrong time sent from the ground would reach both clocks; the ground software checks every command before it is sent [6,~REQ-089], which keeps that case at two failures, and a wrong time that passes that check is an accepted risk. & 2 & 2 & YES \\
\bottomrule
\end{tabularx}}


\field{Choice} Option c, shown in Figure~\ref{fig:clocks}.

\item REQ-135: Every report shall carry the time of both clocks.
\end{itemize}

\subsection{Held Data}
\label{sec:held}
\field{Problem} Radiation can flip single bits in memory (A-5). A command
that waits on board before it runs, the record that an arming command has
arrived, and the data kept over restarts are all checked when they arrive, but
then sit in memory. A bit flipped in that time changes them after the check
and before their use: a changed command could run, or the controller could
take itself to be armed when it is not [5,~Sec.~5.2]. Targets H-6, here a
command acted on in a form the operator did not intend.

\smallskip
{\small\noindent\begin{tabularx}{\textwidth}{@{}l>{\raggedright\arraybackslash}Xcc@{}}
\toprule
 & Option & \sev{H-6}{CRITICAL} & Chosen \\
\midrule
a & Each item is checked once, when it arrives. A bit flipped afterwards goes unnoticed. & 1 & NO \\
b & Each waiting item is stored together with a check value, a number computed from its contents, and the check is repeated just before the item is used. The arming record is stored as a long pattern rather than a single yes-or-no bit, so one flipped bit cannot turn not armed into armed. A flipped bit now goes unnoticed only if a second error makes the check value match as well. & 2 & YES \\
c & Error-correcting memory: memory hardware that finds and repairs a flipped bit on its own. Also two failures, but only if the chip has that feature. & 2 & NO \\
\bottomrule
\end{tabularx}}


\field{Choice} Option b. MCUboot notes the same risk: skipping the check
before use lets an image changed after a good check run unchecked
[9,~Sec.~Integrity Check]. Unlike option c, option b needs no hardware
feature; option c can be added where the hardware has it.

\field{Adds}
\begin{itemize}
\item REQ-136: Every held command and the kept data shall be stored with a check value and checked just before use.
\item REQ-137: The arm state shall be stored so that no single bit error makes it armed.
\end{itemize}

\subsection{Two Kinds of Connection}
\label{sec:links}
\field{Problem} The onboard computer reaches the controller over two
data-link connections, so that losing one does not lose contact (O-3). But if
both connections run through the same driver program at each end, one bug in
that driver cuts both at the same moment (R-1) [5,~Sec.~5.2]. Targets H-4, the
controller no longer commanded or observed. The count is of failures that cut
both connections at once.

\smallskip
{\small\noindent\begin{tabularx}{\textwidth}{@{}l>{\raggedright\arraybackslash}Xcc@{}}
\toprule
 & Option & Failures to cut both & Chosen \\
\midrule
a & Two connections of the same kind, for example two serial lines, served by one driver at each end. One bug in that driver cuts both. & 1 & NO \\
b & Two connections of the same kind, each with its own driver. A fault that comes with that kind of connection, such as a flaw in the chip's hardware for it, still cuts both. & 1 & NO \\
c & Two different kinds of connection, a UART over RS-422 lines and a CAN bus, each with its own driver. Cutting both takes a separate failure in each. & 2 & YES \\
\bottomrule
\end{tabularx}}


\field{Choice} Option c. One connection carries on when the other is
cut (O-3). H-4 still falls to the loss of the onboard computer (R-4), and the
hazard analysis, re-run on this design, finds two failures for it even without
that loss: both connections failing in hardware. The author accepted that risk
[5,~Sec.~8.3].

\field{Adds}
\begin{itemize}
\item REQ-138: The two data-link connections shall be of different kinds.
\end{itemize}
