\section{Introduction}

\subsection{Project Description}

\subsubsection{Background}
\noindent\textbf{Purpose:} The System lets an operator on the ground command,
monitor, and update a controller in space that nobody can reach, and keeps that controller working between contacts.

\medskip
\noindent\textbf{Need:} A controller that nobody can reach must stay operable,
observable, and correctable for its whole life. Operation, observability, and
maintenance including in-flight modification over the specified lifetime are
three areas a space software specification must cover
[3,~Annex~B, items 5.11--5.13, p.~113].

\medskip
\noindent\textbf{Worst-Case Failure:} A failed update can leave the controller
unable to run any firmware and unable to accept new firmware. Without physical
access, that state is permanent.

\medskip
\noindent\textbf{Rationale:} The loss has happened. NASA records a mission
terminated after an in-flight software upload omitted a patch for a defective
countdown timer; its recommendations include test-bed verification of in-flight
software updates [4,~Lesson 0559, p.~199].

\subsubsection{Assumptions and Constraints}
\begin{description}
\item[C-1] The ground cannot talk to the controller directly. Every command,
  report, and firmware image passes through the onboard computer.
\item[C-2] All software is built to NASA's software engineering requirements.
  Rigor per part is set by its software class [5,~Sec.~3.5.1, p.~24; App.~C].
\item[C-3] One engineer builds and checks the System. No independent team
  reviews the work.
\item[C-4] The System runs on commercial development boards, not on spacecraft
  hardware. It can show how the System behaves, not that it would survive
  launch or space.
\item[A-1] Once launched, physical access to the onboard computer or controller
  is impossible; all fixes and updates must arrive by radio.
\item[A-2] The controller can lose power at any moment, even halfway through
  writing new firmware. The System must survive that without losing the
  controller [2,~App.~A, Table~2, p.~63].
\item[A-3] The ground can reach the spacecraft only during line-of-sight
  contact windows \tbd{window}. Between contacts the System must work on its
  own.
\item[A-4] One person operates the ground station. No second person checks a
  command before it is sent, so the System itself must refuse wrong commands.
\item[A-5] Radiation in space can flip single bits in memory, so stored
  firmware can change on its own. The System must not run firmware that has
  changed [2,~App.~A, Table~2, p.~63].
\end{description}

\medskip
{\itshape \noindent\textbf{Note.} A constraint (C) is a limit the System must work
within; it is imposed, not chosen. An assumption (A) is a condition taken as
true without proof; the design depends on it, and if it proves false the design
may be wrong. \textbf{[TBD-$n$]} marks a value not yet known; all are listed
in App.~C.\par}

\subsection{Overview of the Envisioned System}

\subsubsection{Overview}
The System comprises two spatially separated operational segments. The
\textbf{ground segment} on Earth includes the operator, the mission operations
center running ground software, and the ground station antenna
[6,~Sec.~11.2, p.~305]. The \textbf{space segment} in orbit consists of the onboard
computer and the controller, which operate without physical access.

Communication between segments is strictly established via a radio link during
line-of-sight contact windows \tbd{window}. Outside contact windows, the space
segment operates autonomously. Within the spacecraft, the onboard computer
communicates with the controller over the data link during normal operation.
If the controller's main firmware fails to execute, the onboard computer
utilizes the reprogramming link to restore functional firmware independently of
the controller's primary software. Figure~\ref{fig:segments} illustrates this
segment layout.

\begin{figure}[H]
\centering
\includegraphics[width=\textwidth]{fig-segments.pdf}
\caption{Ground and space segments, joined only by the radio link during
contact windows. Inside the spacecraft, the data link handles normal
communication, while the reprogramming link restores working firmware if the
controller's firmware cannot run.}
\label{fig:segments}
\end{figure}

\subsubsection{System Scope}
The system context defines the boundary of the System: the system of interest,
its users, and the external elements that interface with it
[7,~Sec.~8.3, p.~24].

\begin{table}[H]
\centering
\begin{tabular}{@{}ll@{}}
\toprule
Context Element & System Boundary \\
\midrule
System of Interest & Onboard computer, controller, ground software in the MOC \\
Users & Ground operator \\
External Elements & Radio equipment, spacecraft power supply \\
\bottomrule
\end{tabular}
\end{table}

\begin{itemize}
\item \textbf{Enabling systems:} firmware build tools and bench test setups
  required for development and verification, external to operational scope.
\item \textbf{In scope:} commanding, telemetry, firmware updates, and autonomous
  fault handling between contact windows.
\item \textbf{Out of scope:} onboard computer software updates; the
  equipment the controller drives, and its state while no firmware runs; and
  the radio equipment, which is used as given.
\end{itemize}

\section{Description of Envisioned System}

\subsection{Needs, Goals and Objectives}
\label{sec:ngo}
\begin{description}
\item[NEED] A controller that nobody can reach must stay operable, observable
  and correctable for its whole life.
\item[G-1] \textbf{Operability:} the controller keeps running and acts on the
  operator's commands.
  \begin{itemize}[leftmargin=1.2cm]
  \item[\textbf{O-1}] Every valid operator command is executed. Valid means from the
    operator, allowed in the current state, with possible values, and not
    expired.
  \item[\textbf{O-2}] Firmware and commands not from the operator are never acted on.
  \item[\textbf{O-3}] With one data-link connection lost, commands, telemetry and
    updates continue.
  \item[\textbf{O-4}] No fault found between contacts goes unreported.
  \end{itemize}
\item[G-2] \textbf{Observability:} the ground can know what the System is
  doing, how healthy it is, and what happened between contacts.
  \begin{itemize}[leftmargin=1.2cm]
  \item[\textbf{O-5}] No report is lost without the ground being told.
  \end{itemize}
\item[G-3] \textbf{Correctability:} the controller's firmware can be replaced
  for its whole life without losing the controller.
  \begin{itemize}[leftmargin=1.2cm]
  \item[\textbf{O-6}] No update, even one interrupted by a single fault, leaves the
    controller without runnable firmware.
  \end{itemize}
\end{description}

\subsection{Overview of System and Key Elements}
\begin{description}[leftmargin=4.4cm]
\item[Operator] The user. Decides and sends commands, releases new firmware,
  and reads the reports.
\item[Ground software] In the mission operations center. Turns the operator's
  decisions into commands and firmware ready to send, checks them before they
  leave, and keeps every report received.
\item[Onboard computer] Checks every firmware image, and the origin, newness
  and expiry of every command, and passes them to the controller. Stores the
  controller's reports between contacts, watches the controller, and restores
  it when its firmware cannot run.
\item[Controller] Checks every command against its current mode and possible
  values, runs its firmware, acts on commands, reports its state, and returns
  to working firmware on its own when new firmware fails.
\end{description}
The ground station's radio equipment and the spacecraft power supply are
outside the System; it uses them as given.

\subsection{Interfaces}
\noindent\textbf{External interfaces}
\begin{description}[leftmargin=4.4cm]
\item[Operator interface] Human. Ground software to operator. Allows the
  flight operator to issue telecommands, authorize firmware deployments, and
  monitor system telemetry.
\item[Radio link] Radio frequency. Ground software to onboard computer via
  external radio equipment. Provides intermittent telemetry and telecommand
  (TM/TC) transfer exclusively during contact windows.
\item[Power] Electrical. Spacecraft power subsystem to onboard computer and
  controller. Subject to unannounced power interruptions at any time
  (assumption A-2).
\end{description}

\medskip
\noindent\textbf{Interfaces between elements}
\begin{description}[leftmargin=4.4cm]
\item[Data link] Digital data. Onboard computer to controller. Nominal
  interface for commands, telemetry, and firmware updates while controller
  firmware is running. Uses two separate connections, so a single connection
  failure does not interrupt operations.
\item[Reprogramming link] Digital data. Onboard computer to controller.
  Recovery interface used as a last resort to restore functional firmware
  independently of the controller's main software.
\end{description}

\subsection{Modes of Operations}
\noindent\textbf{Life-cycle modes of the System}
\begin{description}[leftmargin=3cm]
\item[Test] Ground bench execution with simulated radio link degradation and
  intentional fault injection to demonstrate operational scenarios.
\item[Operation] Active mission execution using the controller modes detailed
  below.
\item[Disposal] Not applicable; limited to bench demonstration scope.
\end{description}

\medskip
\noindent\textbf{Controller modes during operation}
\begin{description}[leftmargin=3cm]
\item[OPERATE] Nominal state executing confirmed firmware. New firmware images
  can be staged in the background during execution.
\item[TRIAL] Entered upon transitioning to updated firmware. Executes the new
  image for a bounded evaluation window \tbd{trialtime}. If the new image is
  judged good, the update is committed and the controller returns to OPERATE;
  if not, it enters FALLBACK.
\item[FALLBACK] Entered following a failed firmware trial or boot failure.
  Reverts execution to the previous known-good firmware image or the
  last-resort firmware.
\item[RECOVERY] Entered when no operational firmware image can be executed.
  Controller software execution is halted while the onboard computer restores
  functional firmware via the reprogramming link.
\end{description}

\medskip
\needspace{9\baselineskip}
\noindent What works in each controller mode \tbr{modes}:
\begin{table}[H]
\centering
\begin{tabular}{@{}llll@{}}
\toprule
Mode & Commands & Reports & New firmware received \\
\midrule
OPERATE  & YES & YES & YES \\
TRIAL    & YES & YES & NO \\
FALLBACK & YES & YES & YES \\
RECOVERY & NO  & NO  & NO \\
\bottomrule
\end{tabular}
\end{table}
\noindent\textbf{Legend.} YES: available. NO: not available. In RECOVERY, the
onboard computer reports for the controller.

\subsection{Proposed Capabilities}
Each capability is shown in detail by the scenarios in Section~6.0.
\begin{description}[leftmargin=3cm]
\item[Capability-1] \textbf{Telemetry} (serves G-2): regular and event health
  reports, time-tagged, stored between contacts and sent down at the next one,
  with any loss reported.
\item[Capability-2] \textbf{Command handling} (serves G-1): accept only the
  operator's valid telecommands, answer and log every one, support arming and
  time-tagged execution, and replace in flight the means that proves a command
  comes from the operator.
\item[Capability-3] \textbf{Fault handling} (serves G-1): detect faults between
  contacts, respond without the ground, and record them.
\item[Capability-4] \textbf{Update} (serves G-3): receive, check, install and
  judge new firmware, and return to working firmware without outside help if
  it fails \tbd{switch} \tbd{confirm}.
\item[Capability-5] \textbf{Test} (verification only): degrade the radio link;
  cut power or break a data-link connection on command.
\item[Disposal] None; bench demonstration.
\end{description}

\section{Physical Environment}
This section specifies the environment the System encounters across its life
cycle, encompassing simulated mission operations and laboratory integration
and testing. For each environmental condition, the expected system response is
defined as nominal operation, degraded performance tolerance, or survivability
[1,~App.~S, p.~252].

\begin{table}[H]
\centering
\begin{tabularx}{\textwidth}{@{}l>{\raggedright\arraybackslash}Xll@{}}
\toprule
Phase & Environmental condition & Response & Shown on bench \\
\midrule
Operation & Thermal range \tbd{temp} & OPERATE & NO \\
Operation & Vacuum & OPERATE & NO \\
Operation & Radiation: single-event upset / memory bit errors & SURVIVE & SIMULATED \\
Operation & Electrical: power interruption at any instant & SURVIVE & YES \\
Launch & Mechanical: vibration and launch loads & OPERATE & NO \\
Integration and Test & Laboratory bench: ambient room temperature and pressure & OPERATE & YES \\
\bottomrule
\end{tabularx}
\end{table}

\noindent\textbf{Legend: response}
\begin{description}[leftmargin=3.2cm]
\item[OPERATE] All functions continue normally.
\item[TOLERATE] Partial functional degradation occurs, but no function is
  permanently lost.
\item[SURVIVE] Operational functions temporarily halt and automatically recover
  upon removal of the condition.
\end{description}

\medskip
\noindent\textbf{Legend: shown on bench}
\begin{description}[leftmargin=3.2cm]
\item[YES] The condition itself is reproduced on the bench.
\item[SIMULATED] The condition's effect is injected on purpose; the condition
  itself is not reproduced.
\item[NO] Beyond what bench hardware can show (constraint C-4).
\end{description}

\medskip
\noindent\textbf{Transportation:} not applicable; system transportation is
outside the scope of bench demonstration.

\section{Support Environment}
\begin{description}[leftmargin=4.4cm]
\item[Operational planning] The ground operator plans contact windows in
  advance, defining telecommand queues, firmware uploads, and telemetry
  retrieval profiles, with schedule timing derived from orbital parameters
  \tbd{window}.
\item[Commanding and uploads] Ground software formats and validates operator
  telecommands for real-time execution or time-tagged scheduling, while
  verified firmware images are released from the ground segment and uploaded
  across one or multiple contact windows.
\item[Maintenance and repair] Physical maintenance is excluded, as there is no
  physical access in orbit (assumption A-1); anomalies are managed by
  autonomous onboard fault protection or remotely through operator
  telecommands and firmware updates.
\item[Sparing] Physical hardware spares are not available; the onboard
  computer retains a known-good firmware image and the controller maintains
  its last-resort firmware.
\item[Upgrades] Controller firmware updates constitute the sole operational
  upgrade mechanism, governed by a defined release cadence \tbd{frequency},
  while the onboard computer's baseline software remains fixed.
\item[Continued support] Engineering sustainment support remains allocated for
  firmware build, verification, and release throughout the active mission
  life cycle.
\end{description}

\section{Operational Scenarios}
Each scenario follows one thread of events from trigger to outcome
[1,~App.~S, pp.~252--253]. Every scenario below is demonstrated on hardware and
recorded. Sources in brackets are items of NASA's list of software causes of
hazards [2,~App.~A, Table~2].

\subsection{Nominal Conditions}
\begin{description}[leftmargin=3cm]
\item[Scenario-100] \textbf{Firmware update.}
  \begin{enumerate}[nosep]
  \item The operator releases new firmware; the ground software checks it and
    prepares the upload.
  \item Over one or more contacts, the firmware goes up the radio link to the
    onboard computer.
  \item The onboard computer checks that it is undamaged, from the operator,
    built for this controller, and not older than the minimum version.
  \item The onboard computer delivers it to the controller over the data link;
    the controller keeps working meanwhile.
  \item The controller switches to the new firmware and enters TRIAL
    \tbd{switch}.
  \item The new firmware is judged good within the trial time \tbd{trialtime}
    \tbd{confirm}; the update is committed and the controller returns to
    OPERATE.
  \item The outcome is stored and sent down at the next contact.
  \end{enumerate}
\item[Scenario-110] \textbf{Telemetry between contacts.}
  \begin{enumerate}[nosep]
  \item The controller sends regular health reports, and an event report as
    soon as something important happens.
  \item The onboard computer time-tags and stores every report.
  \item At the next contact, all stored reports go down the radio link.
  \end{enumerate}
\item[Scenario-120] \textbf{Command during a contact.}
  \begin{enumerate}[nosep]
  \item The operator decides a command; the ground software prepares and
    checks it.
  \item During a contact, the command goes up the radio link.
  \item The onboard computer checks that it is from the operator, new and not
    expired; the controller checks that it is allowed in the current mode and
    has possible values. Commands added by new firmware are checked the same
    way. A dangerous command must first be armed by a separate command; the arm
    expires if the command does not follow within a set time.
  \item The command is executed. The answers (received, then done with the
    result) go down, and the command and its answers are logged.
  \end{enumerate}
\item[Scenario-130] \textbf{Scheduled command.}
  \begin{enumerate}[nosep]
  \item During a contact, the operator sends a command with a run time; the
    System answers ``received''.
  \item At the run time, the command runs.
  \item The ``done'' answer is stored and sent down at the next contact.
  \end{enumerate}
\end{description}

\subsection{Off-Nominal Conditions}
The off-nominal scenarios cover low performance, operator errors, failures, and
unexpected environmental conditions [1,~App.~S, p.~253]. Each entry gives the
trigger, then the expected outcome.

\medskip
\needspace{4\baselineskip}
\noindent\textbf{Low performance of the radio link}
\begin{description}[leftmargin=3cm]
\item[Scenario-200] The radio link is lost during a firmware upload. The upload
  resumes at the next contact from where it stopped.
\item[Scenario-210] A long gap between contacts fills the report storage on the
  onboard computer. From then on, the System drops the oldest regular health
  reports to make room and keeps every event report. At the next contact, it
  sends what it stored and tells the ground how many health reports were
  dropped and the time span they covered.
\end{description}

\medskip
\needspace{4\baselineskip}
\noindent\textbf{Operator errors and unauthorized commands}
\begin{description}[leftmargin=3cm]
\item[Scenario-300] A command not from the operator, or an old command sent
  again, arrives. It is refused and logged [2,~p.~62].
\item[Scenario-310] A command not allowed in the current mode arrives, for
  example ``switch'' when no new firmware has arrived. It is refused with the
  reason [2,~p.~63].
\item[Scenario-320] A command with impossible values arrives. It is refused with
  the reason [2,~p.~62].
\item[Scenario-330] A dangerous command arrives without being armed. It is
  refused with the reason.
\item[Scenario-335] A dangerous command arrives after its arm has expired. It
  is refused with the reason; the operator must arm again.
\item[Scenario-340] A command arrives after its expiry. It is refused with the
  reason [2,~p.~63].
\item[Scenario-350] An answer is lost and the operator sends the command again.
  It is not run a second time; the answer is ``already done''.
\item[Scenario-360] Firmware built for a different controller is uploaded. It is
  refused before it is installed [2,~p.~63].
\item[Scenario-370] The operator replaces the means that proves commands and
  firmware come from the operator. The new means arrives in a command proven
  with the current one; from then on, only the new one is accepted
  [2,~p.~67].
\end{description}

\medskip
\needspace{4\baselineskip}
\noindent\textbf{Firmware update failures}
\begin{description}[leftmargin=3cm]
\item[Scenario-400] Firmware is damaged in transfer. The onboard computer refuses
  it before it reaches the controller [2,~p.~63].
\item[Scenario-410] Firmware not released by the operator arrives. It is
  refused.
\item[Scenario-420] Firmware older than the minimum version arrives. It is
  refused.
\item[Scenario-425] New firmware arrives during a trial. It is refused with the
  reason until the trial ends [2,~p.~63].
\item[Scenario-430] The new firmware hangs during TRIAL. The controller returns
  to its previous firmware without outside help.
\item[Scenario-440] The new firmware restarts over and over. After
  \tbd{bootcount} failed starts, the controller returns to its previous
  firmware [2,~p.~64].
\item[Scenario-450] The new firmware runs but is never judged good. After the
  trial time, the controller returns to its previous firmware.
\item[Scenario-460] The previous firmware is also unusable. The controller runs
  its last-resort firmware.
\item[Scenario-470] The operator cancels an update in progress. The update stops;
  working firmware is left running.
\item[Scenario-480] No firmware can run. The onboard computer restores the
  last-resort firmware through the reprogramming link and tells the ground at
  the next contact [2,~p.~63].
\end{description}
\noindent In Scenario-430 to Scenario-460, the failed firmware is not started
again unless the operator orders it, and the next reports tell the ground which
firmware now runs.

\medskip
\needspace{4\baselineskip}
\noindent\textbf{Equipment failures}
\begin{description}[leftmargin=3cm]
\item[Scenario-500] One data-link connection fails. Everything continues on the
  other, and the failure is reported.
\item[Scenario-505] A failed data-link connection works again. The System uses
  it again and reports it.
\item[Scenario-510] Both data-link connections fail. The controller keeps
  working on its current firmware, the loss is reported, and the
  reprogramming link is still usable.
\item[Scenario-520] The controller goes silent. The onboard computer notices,
  tries to bring it back, and records what it did.
\item[Scenario-530] A program on the onboard computer crashes. It restarts and
  resumes any update in progress; the controller is not affected.
\item[Scenario-535] The whole onboard computer restarts. The controller keeps
  working. When the onboard computer is back, it resumes any update in
  progress, and no report is lost without the ground being told.
\end{description}

\medskip
\needspace{4\baselineskip}
\noindent\textbf{Unexpected environmental conditions} (from Section~4.0)
\begin{description}[leftmargin=3cm]
\item[Scenario-600] Power is lost while the controller's firmware is being
  written. When power returns, the controller runs its previous firmware, and
  the update can be repeated [2,~p.~63].
\item[Scenario-605] Power is lost during the trial. When power returns, this
  counts as a failed start; after \tbd{bootcount} failed starts, the controller
  returns to its previous firmware.
\item[Scenario-610] A radiation bit error changes stored firmware. The
  controller detects it before starting that firmware and does not run it [2,~p.~63].
\item[Scenario-620] A radiation bit error hits the memory the controller is
  running from. The controller may crash; it restarts on its own and resumes
  operation [2,~p.~63].
\end{description}

\section{Impact Considerations}

\subsection{Environmental Impacts}
None. A bench demonstration creates no orbital debris, contamination or
hazardous waste.

\subsection{Organizational Impacts}
One engineer builds the System and supports it for its whole life. The operator
must know the operating procedures: arming dangerous commands, scheduling
commands, and reading the reports.

\subsection{Technical Impacts}
The System shows, with a recorded result for every scenario, that a controller
nobody can reach can be updated, commanded and monitored without being lost.
The service it provides is fail-safe in-orbit reprogramming of spacecraft controllers.

% ===========================================================================
\section{Risks and Potential Issues}
\begin{description}
\item[R-1] Operations: both data-link connections may share software at each
  end. One defect could cut both at once, leaving only the reprogramming link.
\item[R-2] Implementation approach: code drafted with an AI assistant may
  contain plausible but wrong behaviour. Each subsystem is reviewed and tested
  before it is accepted.
\item[R-3] Staffing: one engineer builds and supports the System. Losing that
  person stops new firmware for the rest of the mission.
\item[R-4] Operations: the System has one onboard computer. If it fails for
  good, the controller keeps running its current firmware but can no longer be
  commanded, observed or updated.
\end{description}
\noindent\textbf{Closeout:} at the end of the project, the documents and the
recorded result of every scenario stay in the repository.

\section{Glossary}
\begin{description}[leftmargin=3.2cm]
\item[Confirmed] Firmware judged good after its trial; only confirmed firmware
  is known-good.
\item[Last-resort] Known-good firmware that updates never replace (golden
  image).
\item[Switch] The controller stops running old firmware and starts the new.
\item[Arm] First step of a dangerous command; changes nothing alone and
  expires after a set time.
\item[Expiry] Time after which a waiting command is refused.
\end{description}
