\section{Introduction}

\subsection{Project Description}

\subsubsection{Background}
\noindent\textbf{Purpose:} The System lets an operator on the ground command,
monitor, and update a controller in space that nobody can reach, and keeps that controller working between contacts.

\medskip
\noindent\textbf{Need:} A controller that nobody can reach must stay operable,
observable, and correctable for its whole life. Operation, observability, and
maintenance including in-flight modification over the specified lifetime are
three areas a space software specification must cover
[3, Annex~B, items 5.11--5.13, p.~113].

\medskip
\noindent\textbf{Worst-Case Failure:} A failed update can leave the controller
unable to run any firmware and unable to accept new firmware. Without physical
access, that state is permanent.

\medskip
\noindent\textbf{Rationale:} The loss has happened. NASA records a mission
terminated after an in-flight software upload omitted a patch for a defective
countdown timer; its recommendations include test-bed verification of in-flight
software updates [4, Lesson 0559, p.~199].

\subsubsection{Assumptions and Constraints}
\begin{description}
\item[C-1] The ground cannot talk to the controller directly. Every command,
  report, and firmware image passes through the onboard computer.
\item[C-2] All software is built to NASA's software engineering requirements.
  Rigor per part is set by its software class [5, Sec.~3.5.1, p.~24; App.~C].
\item[C-3] One engineer builds and checks the System. No independent team
  reviews the work.
\item[C-4] The System runs on commercial development boards, not on spacecraft
  hardware. It can show how the System behaves, not that it would survive
  launch or space.
\item[A-1] Once launched, physical access to the onboard computer or controller
  is impossible; all fixes and updates must arrive by radio.
\item[A-2] The controller can lose power at any moment, even halfway through
  writing new firmware. The System must survive that without losing the
  controller [2, App.~A, Table~2, p.~63].
\item[A-3] The ground can reach the spacecraft only during line-of-sight
  contact windows \tbd{window}. Between contacts the System must work on its
  own.
\item[A-4] One person operates the ground station. No second person checks a
  command before it is sent, so the System itself must refuse wrong commands.
\item[A-5] Radiation in space can flip single bits in memory, so stored
  firmware can change on its own. The System must not run firmware that has
  changed [2, App.~A, Table~2, p.~63].
\end{description}

\medskip
{\itshape \noindent\textbf{Note.} A constraint (C) is a limit the System must work
within; it is imposed, not chosen. An assumption (A) is a condition taken as
true without proof; the design depends on it, and if it proves false the design
may be wrong. \textbf{[TBR-$n$]} marks a proposal the author has not yet
accepted; \textbf{[TBD-$n$]} marks a value not yet known. Both are listed in
App.~C.\par}

\subsection{Overview of the Envisioned System}

\subsubsection{Overview}
The System comprises two spatially separated operational segments. The
\textbf{ground segment} on Earth includes the operator, the mission operations
center running ground software, and the ground station antenna
[6, Sec.~11.2, p.~305]. The \textbf{space segment} in orbit consists of the onboard
computer and the controller, which operate without physical access.

Communication between segments is strictly established via a radio link during
line-of-sight contact windows \tbd{window}. Outside contact windows, the space
segment operates autonomously. Within the spacecraft, the onboard computer
communicates with the controller over the data link during normal operation.
If the controller's main firmware fails to execute, the onboard computer
utilizes the reprogramming link to restore functional firmware independently of
the controller's primary software. Figure~\ref{fig:segments} illustrates this
segment layout.

\begin{figure}[H]
\centering
\includegraphics[width=\textwidth]{fig-segments.pdf}
\caption{Ground and space segments, joined only by the radio link during
contact windows. Inside the spacecraft, the data link handles normal
communication, while the reprogramming link restores working firmware if the
controller's firmware cannot run.}
\label{fig:segments}
\end{figure}

\subsubsection{System Scope}
The scope is the System's boundary: what is inside, who uses it, and what
touches it from outside. NASA calls this the system context
[7, Sec.~8.3, p.~24].

\begin{table}[H]
\centering

\toprule

\midrule

Users & Operator \\
External elements & Radio equipment, spacecraft power supply \\
\bottomrule
\end{tabular}
\end{table}

\begin{itemize}
\item \textbf{Enabling systems:} firmware build tools and the bench test setup,
  needed to build and test the System but not part of it.
\item \textbf{In scope:} commanding, telemetry, firmware updates, and fault
  handling between contacts \tbr{faults}.
\item \textbf{Out of scope:} the onboard computer's own software updates
  \tbr{obcupdate}, and the radio equipment, which is used as given.
\end{itemize}

\section{Description of Envisioned System}

\subsection{Needs, Goals and Objectives}
\label{sec:ngo}
\begin{description}
\item[NEED] A controller that nobody can reach must stay operable, observable
  and correctable for its whole life. The three properties are three areas a
  space software specification must cover: operation, observability, and
  maintenance including in-flight modification over the specified lifetime
  [3, Annex~B, items 5.11--5.13, p.~113].
\item[G-5] Operable: the controller keeps running its function and acts on the
  operator's commands. Capabilities CMD, FM.
\item[G-6] Observable: the ground can know what the System is doing, how
  healthy it is, and what happened between contacts. Capabilities TM.
\item[G-7] Correctable: the controller's firmware can be replaced for its whole
  life without losing the controller. Capabilities UPD.
\item[G-1] No update, and no failure during one, leaves the controller without
  firmware it can run.
\item[G-2] The System acts only on firmware and commands from the operator.
\item[G-3] Losing one connection of the data link stops nothing.
\item[G-4] Between contacts the System handles faults alone and reports them
  later \tbr{faults}.
\item[O-1] Every scenario in Section~6.0 is demonstrated on hardware and
  recorded.
\item[N-1] Retired during drafting; now G-7. NASA requires a single need statement
  [1, Sec.~4.1, p.~49].
\item[N-2] Retired during drafting; now G-6.
\item[N-3] Retired during drafting; now G-5.
\end{description}

\subsection{Overview of System and Key Elements}
\begin{description}[leftmargin=4.4cm]
\item[Operator] Releases firmware, decides commands, reads reports. Works
  through the mission operations center.
\item[Mission operations center] Runs the ground software: commands the
  spacecraft and monitors its performance [6, Sec.~11.2, p.~305]. Packages released
  firmware, checks commands before they are sent, and stores reports.
\item[Ground station] The antenna and radio that carry the radio link
  during contacts [6, Sec.~11.2, p.~305].
\item[Onboard computer] Checks and passes on firmware and commands, stores
  reports, watches and restores the controller.
\item[Controller] Runs its function, reports, keeps known-good firmware to fall back
  on.
\end{description}

\subsection{Interfaces}
\begin{description}[leftmargin=4.4cm]
\item[Radio link] The only connection between the ground and the
  spacecraft. Commands and firmware go up; reports come down. It exists only
  during contact windows.
\item[Data link] The normal path between the onboard computer and the
  controller. Commands and new firmware go to the controller; reports come
  back. It works only while the controller's firmware runs. It has two separate
  connections: if one fails, the other carries everything.
\item[Reprogramming link] The last-resort path, used only when the
  controller's firmware cannot run. It restores working firmware without any
  help from the controller's own software.
\end{description}

\subsection{Modes of Operations}
\begin{description}[leftmargin=3cm]
\item[OPERATE] Runs confirmed firmware. New firmware can arrive \tbr{receive}.
\item[TRIAL] Runs new firmware not yet judged good \tbd{trialtime}.
\item[FALLBACK] Runs previous or last-resort firmware after a failed trial or
  start.
\item[RECOVERY] Runs no firmware. The onboard computer restores it through the
  reprogramming link.
\end{description}

\subsection{Proposed Capabilities}
\begin{description}
\item[TM-1] Send regular health reports: alive, firmware, uptime, last restart
  reason, temperature \tbr{telemetry}.
\item[TM-2] Report important events at once \tbr{telemetry}.
\item[TM-3] Timestamp every report \tbr{telemetry}.
\item[TM-4] Store reports between contacts, send all at the next one, report any
  lost.
\item[TM-5] Report the health of each data-link connection \tbr{telemetry}.
\item[CMD-1] Accept commands only from the operator. Refuse replayed commands.
\item[CMD-2] Answer every command: received, refused with reason, or done with
  result.
\item[CMD-3] Refuse commands not allowed in the current state.
\item[CMD-4] Run a resent command at most once.
\item[CMD-5] Dangerous commands need two steps: arm, then execute.
\item[CMD-6] Refuse impossible values.
\item[CMD-7] Let the operator cancel an update, leaving known-good firmware
  running.
\item[CMD-8] Run commands at a set time. Refuse expired commands.
\item[CMD-9] Log every command and its answer.
\item[FM-1] Notice a silent controller and try to bring it back \tbr{faults}.
\item[FM-2] Carry on over the other connection when one dies \tbr{faults}.
\item[FM-3] Restart crashed onboard programs and continue \tbr{faults}.
\item[FM-4] Record every fault and action for the ground \tbr{faults}.
\item[UPD-1] Take firmware from the ground through dropping links.
\item[UPD-2] Refuse firmware that is damaged, not from the operator, for
  something else, or below the minimum version.
\item[UPD-3] Get the firmware to the controller.
\item[UPD-4] Switch the controller to it \tbd{switch}.
\item[UPD-5] Decide whether it is good \tbd{confirm}.
\item[UPD-6] Go back to working firmware if not, with nobody's help.
\item[UPD-7] Tell the ground what happened.
\item[UPD-8] Never leave the controller without runnable firmware.
\item[VER-1] Degrade the radio link on purpose (test only).
\item[VER-2] Cut controller power and break one connection on command (test
  only) \tbr{faultinject}.
\end{description}

\section{Support Environment}
Firmware is built and released on the ground and sent up during contacts, one
transfer across several if needed. The onboard computer keeps the last
known-good firmware. Update rate \tbd{frequency}. Nothing is repaired after
deployment.

\section{Operational Scenarios}

\subsection{Nominal Conditions}
\begin{description}
\item[OPS-100] Update: release, upload over one or more contacts, check,
  transfer \tbr{receive}, switch \tbd{switch}, judged good \tbd{confirm},
  confirmed, outcome reported.
\item[OPS-110] Telemetry: reports stamped and stored between contacts, all sent
  at the next one.
\item[OPS-120] Scheduled command: received during a contact, runs at its time,
  answer sent at the next contact.
\end{description}

\subsection{Off-Nominal Conditions}
Trigger, then expected outcome. Sources in brackets are items of [2, App.~A,
Table~2].
\begin{description}
\item[OPS-200] Ground link lost mid-transfer: resumes next contact where it
  stopped.
\item[OPS-210] Command not from operator or replayed: refused, logged [2, p.~62].
\item[OPS-220] Answer lost, command resent: not run again, ``already done''.
\item[OPS-230] Command wrong for current state: refused with reason [2, p.~63].
\item[OPS-240] Impossible value: refused with reason [2, p.~62].
\item[OPS-250] Dangerous command not armed: refused with reason.
\item[OPS-260] Command expired: refused with reason [2, p.~63].
\item[OPS-270] Report storage full: ground told how many were lost.
\item[OPS-300] Firmware damaged in transfer: refused before the controller
  [2, p.~63].
\item[OPS-310] Firmware not from operator: refused.
\item[OPS-320] Firmware below minimum version: refused.
\item[OPS-330] Firmware for another controller: refused [2, p.~63].
\item[OPS-340] Power lost during firmware write: previous firmware runs; retry
  possible [2, p.~63].
\item[OPS-350] New firmware hangs: back to previous, unaided.
\item[OPS-360] New firmware restart loop: back to previous after \tbd{bootcount}
  starts [2, p.~64].
\item[OPS-370] New firmware never judged good: back to previous.
\item[OPS-380] Previous firmware also bad: last-resort firmware runs.
\item[OPS-390] Operator cancels update: known-good firmware left running.
\item[OPS-400] Bit error in stored firmware: detected, not run \tbr{bitflip}
  [2, p.~63].
\item[OPS-410] No firmware can run: restored through the reprogramming link
  [2, p.~63].
\item[OPS-500] One data-link connection fails: everything continues on the
  other; reported.
\item[OPS-510] Both data-link connections fail: controller keeps working; loss
  reported; reprogramming link still usable \tbr{bothlinks}.
\item[OPS-520] Controller silent: noticed, recovery tried, recorded
  \tbr{faults}.
\item[OPS-530] Onboard program crash: it restarts and resumes any update; the
  controller is unaffected \tbr{faults}.
\end{description}

\section{Risks and Potential Issues}
\begin{description}
\item[R-1] Both data-link connections may share software; one defect could cut
  both.
\item[R-2] Controller memory may not hold last-resort plus two working firmwares.
\item[R-3] Second data-link connection and reprogramming link not yet shown on
  bench.
\item[R-4] Demonstration date \tbd{date}; undemonstrated scenarios are declared,
  not dropped.
\end{description}

\section{Glossary}
\begin{description}[leftmargin=3.2cm]
\item[Confirmed] Firmware judged good after its trial; only confirmed firmware
  is known-good.
\item[Last-resort] Known-good firmware that updates never replace (golden
  image).
\item[Switch] The controller stops running old firmware and starts the new.
\item[Arm] First step of a dangerous command; changes nothing alone.
\item[Expiry] Time after which a waiting command is refused.
\end{description}
